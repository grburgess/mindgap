# inbox-to-mindmap

A folder is a staging area, not a filing cabinet. The user drops documents into
`~/second_brain/inbox/`; this skill reads them, puts the **information** into the
graph, and archives the file to `~/second_brain/raw/`. The documents themselves
never become nodes — each one survives only as a `file://` provenance URL (to
its archived location) on the claims it produced.

That distinction is the whole point. A node called "Q3 architecture review deck"
is a filename with extra steps: to use it you have to re-open the deck. A node
called "Hybrid BM25 + dense retrieval beat dense-only by 14 points on internal
eval" is knowledge — it answers a question on its own, links to other ideas, and
gains confidence when a second document says the same thing. Nodes shaped like
documents make a graph that mirrors a directory; nodes shaped like claims make a
graph that thinks.

The binding ingest protocol is `AGENTS.md`. The rules that
matter most here are repeated below.

## Layout

| Thing | Default | Override |
|---|---|---|
| Inbox folder | `~/second_brain/inbox/` | `$MINDGAP_INBOX`, or a path the user names |
| Archive | `~/second_brain/raw/` | — |
| Ledger | `~/.mindgap/inbox-ledger.json` | `--ledger` |

The inbox is a drop zone, not a home: once a file's claims have landed (or it is
marked skipped), it MOVES to the archive — `~/second_brain/raw/YYYY/<topic>/`
(S9.5). Files are never renamed beyond collision handling and never deleted; the
archive is immutable ground truth. The ledger records `sha256 → what was
ingested`, and dedup is by content hash, so moves are safe: a second run over the
emptied inbox does nothing, and an *edited* re-drop returns as `changed` and gets
re-read. If the inbox does not exist, say so and offer to create it rather than
inventing a different path.

## Pipeline

### S1 — Scan (recursive)
```
python3 <skill>/scripts/scan_inbox.py [DIR] > /tmp/inbox.json
```
Walks the whole tree, at any depth. Every pending file comes back with `status`
(`new`, `changed`, `done`, `unsupported`, `skipped-large`), its `rel` path, its
`folder`, and the folder's `segments`. The same records are also grouped under
`folders`, each with its `context_files` listed separately.

Report the counts up front ("6 new across 3 folders, 1 changed, 4 already
ingested, 1 unsupported (.key)") so the user knows the scope before you spend
tokens on it. Work through `new` and `changed` files only.

Dedup is by content hash across the *whole* tree, so a file re-exported into a
second folder under a different name is recognised as already done and never
resurfaces. Say so when it happens — otherwise an operator who dropped a
re-export thinks you missed it.

**The folder is live.** People keep dropping files while you work. Scan again
before you report (S10); if anything is pending, go back to S1.5 and process it.
A single scan at the start is how you silently ingest half a dump and call it
done.

### S1.5 — Read the folder structure as context
People sort things before they dump them, and that sorting is information the
files themselves don't repeat. A deck sitting in `market-research/vendor-evals/`
is telling you what it is about before you open it. Use it:

- **Work one folder at a time**, not one file at a time. Documents in a folder
  are usually facets of the same subject, so reading them together lets you spot
  the claim that three of them share — that is one strong node, not three weak
  duplicates. File-at-a-time processing misses this entirely.
- **Read the folder's context file first** if `context_files` lists one
  (`README.md`, `_context.md`, `notes.md`, …). The user wrote it to explain what
  the dump is, so it is framing for everything beside it rather than a source of
  *subject-matter* claims. But it is often the only place a **method** is
  written down — how the export was produced, what window it reaches, what it
  systematically omits ("Teams channels reach ~5 weeks back, root messages only,
  no thread replies"). Those are durable and belong in the graph: ingest them as
  method/provenance claims, typed `learning` or `reference`. A context file is
  still subject to the S3 value gate like anything else — plenty of READMEs say
  only "files I dumped on Tuesday", and those produce nothing. Tell the user what
  the context file framed and which method claims (if any) you took from it.
- **Path segments are topic signal.** `market-research/vendor-evals/deck.pptx`
  says the claims inside concern market research and vendor evaluation. Feed those
  terms into the S4 graph lookup — they are often better search terms than
  anything in the document's own prose.
- **Nesting is narrowing.** Outer segments are the broad subject, inner ones the
  specific cut. Prefer the innermost meaningful segment when it conflicts with
  an outer one.
- **Ignore junk segments.** Two kinds carry no topic. *Filing noise* —
  `Downloads`, `New Folder`, `untitled`, `misc`, `v2 final`, bare dates (a date
  folder says *when* it was dumped; put that in the body if it matters, not in a
  tag). And *source-type segments* — `chats`, `channels`, `mail`, `exports`,
  `transcripts`, `teams_chat`, `slack` — which describe where content came from,
  not what it is about. A whole tree can be source-type all the way down; when
  that happens S1.5 gives you nothing and the documents' own terms carry the
  work. Say so rather than manufacturing tags from filing structure.

Folder context is a prior, not a fact. If a document's contents contradict the
folder it sits in, the contents win — say so in your report rather than filing
the claim under a label it doesn't deserve.

### S2 — Get the text
Two paths, by extension:

- **Read tool** — `.pdf` (read page ranges; page numbers are your locators),
  `.png/.jpg/.gif/.webp` (you see images directly — diagrams, whiteboard photos,
  screenshotted slides), `.md/.txt/.rst`.
- **`scripts/extract_text.py FILE`** — `.docx`, `.pptx`, `.xlsx`, `.html`,
  `.eml`, `.csv`, `.tsv`. It emits section markers (`[slide 3]`, `[sheet: Losses]`,
  `[§ Heading]`) precisely so you can cite where a claim came from.

For a long PDF, read the abstract/intro/conclusions first and only go deeper
where the information density justifies it. You are hunting claims, not
producing a summary of every page.

### S3 — Value gate
Ask: does this document contain something worth knowing six months from now?
Receipts, invoices, boarding passes, calendar invites, credential dumps, and
"here's the file you asked for" emails do not. Skip them, mark them skipped with
a reason, and move on — a graph polluted with transactional debris is worse than
a smaller honest one. Personal or sensitive material (financial statements,
medical records, credentials) stays out unless the user explicitly asks for it.

### S4 — Read the graph before you write to it
You need two things here: **anchors** to link new claims to, and **existing
nodes** that already state the claim you are about to mint. Skipping this is how
duplicates get born. Do it once per folder, not once per file — the anchors are
nearly always shared.

**Survey with a projection, not the raw tool.** On a mature graph the MCP
`mindgap_find` returns full node bodies with no limit — a single one-word
query can come back tens of thousands of characters and blow your context on
material you only wanted titles from. Survey through the CLI instead, and open
full nodes only for the handful you actually intend to touch:

```
mindgap find "<term>" --json | jq '.[] | {id, title, type}'
mindgap show <id> --json          # only for candidates you'll link or upsert
```

**One word per query.** Multi-word strings fail in both tools, and `context`
fails worse than `find`: `find` degrades into noise you can see, while
`context "vendor evaluation criteria taxonomy"` returns `matched: 0` on
a graph holding a hundred vendor-evaluation nodes. An empty result is never evidence that
nothing exists — it usually means your query was too specific. Re-query with
single salient terms before concluding a claim is new.

### S5 — Distill claims
One document yields roughly 1–8 nodes. Fewer than one means the value gate
should have caught it; more than eight usually means you are transcribing rather
than distilling. It is a smell, not a cap — an already-distilled digest (a
meeting-notes file that is itself a summary of twenty messages across five
topics) can honestly carry more. Exceed it deliberately and say why in your
report; don't drop real claims to hit a number.

The test for a claim node: **would this still make sense to someone who never
sees the file?** If the body says "the approach described in section 3", it
fails — inline what section 3 actually said.

- `id` — kebab-case slug naming the claim, not the file:
  `hybrid-retrieval-beats-dense-only`, not `q3-deck-slide-7`.
- `type` — from the AGENTS.md vocabulary: `concept | definition | learning |
  design | feature | software | repo | person | team | jira-ticket`. Most dumped
  documents yield `learning` (something found to be true) or `concept`/`design`.
- `title` — the claim in a phrase a human would recognize later.
- `body` — ≥40 words: what is claimed, what it rests on (numbers, conditions,
  scope), and why it matters here. Use exact-id `[[wiki-links]]` to anchors.
  Carry over the caveats: "on our internal eval, n≈2k" is part of the claim.
- `tags` — the claim's own subject terms, plus any folder segment that reads as
  a topic (`market-research`, `vendor-evals`). Junk segments never become tags.
- `confidence` — 0.6 for a single undated source; lower if the document hedges.
- `created_by` — `skill:inbox-to-mindmap`.
- `urls` — see below.

### S6 — Provenance
Every node from a document carries a locator that points back at the exact spot.
The `url` points at the **archive destination** (where S9.5 will move the file),
not the inbox path it currently sits at — compute the destination first:
`~/second_brain/raw/YYYY/<topic>/<filename>`, where `YYYY` is the ingest year and
`<topic>` is the innermost meaningful folder segment (S1.5 rules), else the
primary claim tag; a name collision in the destination appends the file's first
8 sha256 hex chars before the extension.

```json
"urls": [{"label": "dump: retrieval/q3-review.pptx — slide 7",
          "url": "file:///Users/you/second_brain/raw/2026/retrieval/q3-review.pptx",
          "kind": "file"}]
```

The label uses the path **relative to the inbox**, not the bare filename — three
folders can each hold a `notes.md`, and "dump: notes.md — p. 2" would point at
none of them.

Percent-encode the URL path: real dump folders contain spaces and worse (a
folder named `teams_chat ` with a trailing space is not hypothetical). Spaces
become `%20`. The human-readable label keeps the raw path; only the `url` is
encoded.

| Format | Locator |
|---|---|
| PDF | `p. 12` |
| pptx | `slide 7` (add `notes` if that's where it came from) |
| docx | `§ <heading text>` |
| xlsx | `sheet: Losses` |
| eml | `email — <subject>, <date>` |
| html | `<page title>` |
| md / txt | `§ <heading>`; for chat exports, `§ <heading>, <speaker> <date>` |
| image | the filename alone |

Chat and message exports are the common case for md/txt, and there the locator
that actually helps is **who said it and when** — a heading alone points at
twenty bullets from five people. Carry the speaker and ISO date whenever the
source marks them.

A claim you cannot locate is a claim you cannot check later. If you truly cannot
pin it down, say so in the label (`whole document`) rather than inventing a page
number.

### S7 — Dedup raises confidence
Dedup twice: across the folder you just read, then against the graph.

Siblings first — if three decks in `vendor-evals/` all say the vendor's API
rate-limits at 10 rps, that is **one** node whose body cites all three files
(three `urls` entries) at a confidence well above 0.6, not three nodes saying
the same thing. Independent documents agreeing is the strongest signal a dump
folder produces; splitting it into duplicates throws that signal away.

Then, if S4 found a node already asserting this claim, **upsert that node** instead of
minting a near-duplicate: merge any new specifics into the body, append this
file's URL to `urls`, and raise `confidence` (0.6 → 0.8, or → 1.0 if the sources
are genuinely independent).

Upsert replaces scalar fields, and that makes two of them destructive:

- **Fetch the FULL body first** (`mindgap show <id> --json`) and write back
  the whole thing plus your additions. A body composed from a truncated read
  silently deletes everything you didn't see. If you can't retrieve the full
  body, mint nothing and say why — a lost body is unrecoverable, a deferred
  claim is not.

  Don't retype it. Build the payload programmatically so the original text is
  copied rather than reproduced from memory, and assert that it survived:

  ```python
  existing = json.load(open("node.json"))          # mindgap show <id> --json
  new_body = existing["body"] + "\n\n" + addition
  assert existing["body"] in new_body              # refuses to write a truncation
  ```

  A 2,400-character body retyped through a heredoc is one dropped paragraph away
  from silent data loss, and nothing downstream will tell you it happened.
- **Preserve the existing `created_by`.** It records where the node came from,
  and overwriting it erases that origin (a node first written by
  `capture:some-session` should not end up attributed to this skill). Pass the
  node's current value back unchanged; your contribution is already recorded by
  the `urls` entry you appended. Edges you add carry your own `created_by`. Two documents agreeing is exactly the independent
re-verification AGENTS.md asks for — that is a strengthened node, not a second
one. If the new document *contradicts* an existing node, do not silently
overwrite: keep both readings in the body, note the disagreement and each
source, and lower confidence.

### S8 — Link with evidence
Every node needs at least one edge or exact-id wiki-link to a **pre-existing**
node — `relates_to`, `depends_on`, `implements`, `part_of`, `defines`. Islands
are unreachable and effectively lost.

Use exact node ids (`[[repo-maestro]]`, never `[[maestro]]`); verify with
`mindgap find` first. Claims from the same document link to each other
*only where a real relation holds* — do not wire them into a clique, because
that just re-encodes the document shape you were avoiding. If no honest link
exists, connect to the closest genuine shared concept and say why in the body.
Never invent a relationship to satisfy the rule.

### S9 — Ingest, then mark the ledger
Prefer the **MCP** `mindgap_ingest` (validates the whole payload, refuses
dangling endpoints, returns persisted rows) — *unless you are working against a
non-default graph*. The MCP server is bound to whatever DB its process started
with and ignores `MINDGAP_DB` in your environment, so on any other graph it
writes to the wrong place while reporting success. There, use the CLI and export
the variable in every shell call (a shell does not persist between calls):

```
export MINDGAP_DB=/path/to/graph.db && mindgap stats   # confirm target first
```

The CLI form:

```
mindgap ingest - <<'EOF'
{"nodes": [...], "edges": [...]}
EOF
```

Only after the write lands, record it — the ledger must reflect the graph, never
your intent:

```
python3 <skill>/scripts/scan_inbox.py --mark - <INBOX_DIR> --ledger <LEDGER> <<'EOF'
{"marks": [
  {"path": "/Users/you/second_brain/inbox/retrieval/q3-review.pptx",
   "node_ids": ["hybrid-retrieval-beats-dense-only", "chunk-size-512-sweet-spot"]},
  {"path": "/Users/you/second_brain/inbox/underwriting/receipt.pdf",
   "outcome": "skipped", "note": "transactional receipt, no durable claim"}
]}
EOF
```

Mark skipped files too, so the next run doesn't re-read them.

**Pass the same inbox dir you scanned with.** `--mark` reports how many files
remain pending, and it can only count them in a folder you name. Omit the dir
and it returns `still_pending: null` rather than guessing — because guessing
means counting the *default* inbox's backlog, which reads as "you still have 28
files" and sends you off to ingest a tree that was never in scope.

### S9.5 — Archive
Order matters: **ingest (urls already point at the destination, S6) → mark (S9)
→ move.** `--mark` hashes the file at the path you pass, so a file moved before
marking comes back `missing` and never enters the ledger — mark it while it
still sits in the inbox, then move. Move every processed file — ingested *and*
skipped — to its computed destination:

```
mkdir -p ~/second_brain/raw/2026/retrieval
mv "<inbox>/retrieval/q3-review.pptx" ~/second_brain/raw/2026/retrieval/q3-review.pptx
```

Context files move with their folder (destination = the topic they framed). An
emptied inbox subfolder is removed. If a move fails, report it, mark the ledger
with a note, and leave the file — the node's `url` dangles until the move is
retried, and saying so beats silently pointing provenance at nothing. Only files
under the inbox move; a user-named folder elsewhere (an override run) is
ingested in place with `url`s at its real location — archiving is inbox
semantics, not a property of ingestion.

### S10 — Re-scan, then report
Scan once more before writing the report. `--mark` tells you what you just
recorded and, at the foot, how many files are still pending — if that number is
not zero (someone added more while you worked), return to S1.5 and process them.
Only report when a fresh scan comes back empty.

One table, then one line of judgment:

```
retrieval/                    (README.md framed this folder)
  q3-review.pptx    3 new, 1 upserted (retrieval-eval-protocol → conf 0.8)
  bench-notes.md    1 merged into hybrid-retrieval-beats-dense-only (conf → 0.9)
underwriting/
  losses.xlsx       1 new (southeast-loss-ratio-elevated)
  receipt.pdf       skipped — transactional
(root)
  scan.key          unsupported (.key) — export to PDF and re-drop
```
Then name the most interesting thing the batch added and what it connected to.
That sentence is what the user actually reads.

Finally, snapshot the graph (`mindgap export`, AGENTS.md rule 6) — a batch
ingest is exactly the change worth having a rollback point for. On a non-default
graph pass `--out` somewhere outside `~/.mindgap/snapshots/`, so a test run
doesn't leave a stray snapshot among the real ones.

## Worked example

Input (`notes.docx`, under heading "Retrieval Findings"):

> Hybrid BM25 + dense retrieval beat dense-only by 14 points on our internal
> eval. Chunk size of 512 tokens was the sweet spot; 1024 lost precision.

Two claims, no document node:

```json
{"nodes": [
  {"id": "hybrid-retrieval-beats-dense-only",
   "title": "Hybrid BM25 + dense retrieval beats dense-only by ~14 points",
   "type": "learning",
   "body": "On an internal evaluation, combining BM25 lexical retrieval with dense vector retrieval outperformed dense-only retrieval by 14 points. The gain is attributed to lexical matching catching exact-term queries that embeddings blur. Relevant to any [[retrieval-augmented-generation]] pipeline choosing a single retriever; the eval was internal and unpublished, so treat the magnitude as indicative rather than benchmarked.",
   "tags": ["retrieval", "rag"],
   "urls": [{"label": "dump: notes.docx — § Retrieval Findings",
             "url": "file:///Users/you/second_brain/raw/2026/retrieval/notes.docx", "kind": "file"}],
   "confidence": 0.6, "created_by": "skill:inbox-to-mindmap"},

  {"id": "chunk-size-512-sweet-spot",
   "title": "512-token chunks outperformed 1024 for retrieval precision",
   "type": "learning",
   "body": "Chunking documents at 512 tokens gave the best retrieval precision in the same internal eval; 1024-token chunks diluted the embedding and lost precision. A concrete default for [[retrieval-augmented-generation]] indexing work — no result was reported below 512, so the lower bound is untested.",
   "tags": ["retrieval", "chunking"],
   "urls": [{"label": "dump: notes.docx — § Retrieval Findings",
             "url": "file:///Users/you/second_brain/raw/2026/retrieval/notes.docx", "kind": "file"}],
   "confidence": 0.6, "created_by": "skill:inbox-to-mindmap"}
],
 "edges": [
  {"src": "chunk-size-512-sweet-spot", "dst": "hybrid-retrieval-beats-dense-only",
   "rel": "relates_to", "created_by": "skill:inbox-to-mindmap"}
]}
```

Note what is absent: no `notes-docx` node, no "Q3 findings document" node. The
file is in the URLs, where it belongs.

## Degradation

| Situation | Action |
|---|---|
| Inbox folder missing | report the path checked; offer to create it — don't guess another folder |
| Legacy `~/mindmap_ingest/` content | leave in place — its provenance URLs must keep resolving; do not migrate or re-ingest |
| Everything already ingested | say "nothing pending" and stop; do not re-ingest to look busy |
| `unsupported` extension (.key, .pages, .zip) | list it and suggest exporting to PDF; never fabricate contents |
| PDF is scanned images | read it as images via the Read tool; if illegible, mark skipped with the reason |
| File is a research paper | `paper-to-mindmap` handles papers better (author line, arXiv URL, `paper` node). Hand off rather than flattening it into claims |
| Document is mostly a big table | extract the *findings* the table supports, not the rows; the file stays the record of the raw numbers |
| Folder context file contradicts the documents | the documents win; note the mismatch in your report |
| Deeply nested tree, one file per folder | the structure is filing, not topic — fall back to the documents' own terms |
| Whole inbox is flat (no folders) | nothing lost; skip S1.5's folder signal and use document terms alone |
| MCP and CLI both unreachable | report the blocker and leave the ledger untouched, so nothing is silently lost |
