# Loop Distill

<!-- The global-learnings ledgers this skill reads and writes live at
     $MINDGAP_HOME/learning/<skill>/. This skill owns no ledger of its own. -->

A project grows loops; each loop's memory is local to itself and knows
nothing of its siblings. This is the reconciler: one pass over every
`self-learning-loop/*/` and `meta-training/*/` (meta-trainer run) in a
project, yielding one ledger, a health audit of the loops, and a small
set of gated promotions outward. "Loop" below covers both unless a rule
names meta-training explicitly. It is
read-mostly, and it is never a gate — nothing found here can fail a loop.

## Hierarchy

```
GLOBAL   global-learnings.md  +  mindgap
         ~/.claude/skills/**                        (tier-2, gated)
   |
PROJECT  <project>/CLAUDE.md            <- one marked block, gated diff
         <project>/.claude/PROJECT-LEARNINGS.md     <- ledger, authoritative
   |
LOOP     self-learning-loop/<name>/{GOAL,STATE,STRATEGY}.md
         meta-training/<name>/{GOAL.md,STATE.json + STATE.md render}
         <project>/.claude/skills/<loop>-lessons/   (optional)
```

Each layer reads the one above it: a loop reads the ledger at RESUME, the
ledger reads global learnings, and every session in the project reads the
marked `CLAUDE.md` block. This skill owns the PROJECT layer — it rewrites
the ledger outright, proposes the `CLAUDE.md` block, and touches the
layers above and below it only under the phase-5 gates.

## Phase 0 · discover & lock

Locate, in this order: the project root; every
`self-learning-loop/*/STATE.md` AND every `meta-training/*/STATE.json`
beneath it; the ledger at
`<project>/.claude/PROJECT-LEARNINGS.md`; the project `CLAUDE.md`;
`<project>/.claude/skills/*-lessons/`.

A meta-training run's STATE.md is a RENDER of STATE.json (`meta_loop`'s
state of record) — read both, but this skill NEVER writes either: no
stuck reset, no `## Consult` seeding, no memory-section edit. Every fix
on a meta-training run is proposed in ledger §7, and the field mapping
for the audit checks is in `references/audit-checks.md` § Meta-training
runs.

- **Live-loop guard first** (`references/audit-checks.md`). A loop is LIVE
  only when its STATE shows `session-in-progress: yes` **and** its STATE
  mtime is under 6h. Audit a live loop read-only, never rewrite its STATE,
  and mark it `live` in ledger §2 — racing a running session corrupts the
  memory it is mid-write on. Both halves are required: an in-progress flag
  over an mtime older than 6h is a `stuck` loop, not a live one, and phase
  2 resets it.
- **No loops found → report and stop.** Do not scaffold a ledger for a
  project that never ran a loop; an empty ledger is a file nobody reads
  and a claim about this project that isn't true.
- Loops present but no ledger → create it from
  `templates/PROJECT-LEARNINGS.md`. `loop-system` seeds it at INIT, so a
  missing ledger means the project predates that.

## Phase 1 · read

The orchestrator reads and INLINES everything later phases judge on:

- every STATE.md in full — verified facts, general rules, open failures,
  iteration log, `## Auto mode`;
- GOAL.md §1–2 (goal + done-criteria) per loop; STRATEGY.md when present;
- unresolved `## Structure pass` proposals and `## Memory check` flags —
  they accumulate unread unless this pass consumes them;
- project skills, the project `CLAUDE.md`, and the prior ledger.

**Context diet — the rule this phase exists to protect.** Never hand a
subagent file paths to go read. Read-heavy panel subagents autocompact-
thrash and stall, burning the session and returning nothing
(`gl-2026-07-02-panel-context-diet`). A subagent gets inlined text, one
question, and nothing else. The orchestrator holding every STATE in
context is also what makes the cross-loop contradiction hunt possible at
all — no single-loop reader can see a contradiction between two loops.

## Phase 2 · mechanical audit

Run the nine checks in `references/audit-checks.md`; flags, thresholds,
evidence format, and the contradiction hunt all live there. Spend no
verification budget — every check is decidable from the filesystem, the
STATEs, and mindgap id lookups.

Restated here because misreading it is how this phase does damage: **fix
only what is mechanically provable** — a dead `map:` id that still
re-resolves or re-ingests, a `stuck` flag whose STATE mtime is >24h AND
whose `Last session` date is not today, a missing `## Consult` line in a
non-live loop — and log each fix to ledger §9. Everything semantic
(closing an `unclosed` loop, retiring a `stale` fact, resolving a
contradiction) is proposed, never applied. A wrong auto-fix rewrites
memory that every later session then trusts.

Two boundaries inside "mechanically provable" that a completion-optimising
run erodes:

- **`stuck` detection ≠ `stuck` reset.** Detection flags at STATE mtime
  >6h; the automatic reset additionally requires mtime **>24h** AND the
  `Last session` date **not today**. `session-in-progress` is
  `loop-system`'s only double-run guard, and a session with one long
  iteration — a big build, a wide test matrix — is slow, not abandoned.
  Clear it and two sessions write one STATE. Anything short of both
  conditions is flagged in §6, never reset.
- **A `dead-map` id is never synthesised.** Re-resolve by date +
  loop-name tag, or re-ingest. Neither available (MCP down, node
  hard-deleted) → leave the dead id in place and flag it in §6. An
  invented id is a false reference written into a loop's memory.

## Phase 3 · distill

Route each candidate with the table in
`references/promotion-protocol.md`. One line is worth restating because
it is the whole point: **exactly one destination per learning.** A rule
written into both the ledger and `CLAUDE.md`, or into both a project
skill and global learnings, rots in at least one of them — the copies
drift and no reader can tell which is current. The one apparent
double-match is not one: the `CLAUDE.md` block is a **projection of
qualifying §4 rules, not a rival destination** — a rule lives in §4 and is
*mirrored* into the block when it qualifies. That is what keeps "exactly
one destination" true when both the project-scoped row and the
every-session row appear to match.

Dedup against **every** destination in that table before writing, not only
the one you routed to; an equivalent row already present anywhere gets its
`used:`/`last:` bumped instead of a near-duplicate appended — **with one
exception.** A row that `loop-system`'s own SESSION END step 2 appended
earlier in THIS session has never met a verifier (step 2 writes tier-1
rows unverified; step 3 then invokes this skill). Treat such a row as an
unverified candidate and route it through phase 4, rather than seeing it
already present and merely bumping its `used:`. Otherwise the single
largest source of new global rows reaches the global layer unverified, and
phase 4's "cost scales with reach" is defeated by step ordering.

Rows carry the global-learnings usage suffix byte-identically:
`used:<n> last:<YYYY-MM-DD>`. Usage, not recency, drives prune/promote.

## Phase 4 · verify on promotion

Verification cost scales with reach, so only candidates bound for
`CLAUDE.md`, global learnings, **or a skill** are re-verified: a stale
ledger row costs one project, a stale global row costs every project, and a
stale SKILL rule costs every project on every task the skill triggers on —
the highest reach in the system. Protocol in
`references/promotion-protocol.md` — one independent verifier subagent per
candidate, receiving the fact AND its check procedure inlined, and never
loop reasoning, chat, or a file path to go read.

**Skill candidates verify the FACT, never the generalisation.** A skill rule
is a procedure; this phase can only establish that the observation behind it
still holds. `HOLDS` on "the loop stalled twice on X" does NOT license
"therefore always do Y" — the verifier is deliberately blind to the
generalisation step, so the leap from fact to rule stays a human judgement at
the phase-5 gate. Never let a `HOLDS` verdict read as endorsement of the rule
it motivated: that would put a verification badge on an unverified write,
which is worse than the honest absence of one.

Verdict schema: **`HOLDS` | `STALE` | `UNPROVABLE`, plus one evidence
line.** `STALE` demotes to ledger §6 carrying that evidence and is never
promoted. `UNPROVABLE` stays in the ledger marked
`unverified since <date>`, as does everything outside the promotion set.
Nothing is silently trusted.

**Subagents unavailable → never self-verify.** Where a verifier cannot be
spawned — this skill invoked inside a subagent, nesting impossible — do
NOT verify inline and call it verified. That is the fake-verification
failure `loop-system` already forbids (`loop-system/SKILL.md` § Errors,
"Subagent spawning unavailable"), and it is the natural degradation
precisely because it looks like finishing the job. Mark the candidate
`UNPROVABLE`, **withhold the promotion**, and say so in the phase-7
report. An unattended self-verified promotion is the exact artifact this
layer exists to prevent.

## Phase 5 · write

| surface | gate |
|---|---|
| `.claude/PROJECT-LEARNINGS.md` | auto (full rewrite) |
| non-live `self-learning-loop/*/STATE.md` | auto, mechanical fixes only (stuck-flag reset, `## Consult` seeding) — never edits a live loop's STATE, **never rewrites its memory sections** |
| `meta-training/*/` (STATE.json or STATE.md) | **never** — audit read-only; every fix is a §7 proposal (STATE.md is a render; `meta-trainer` owns both files) |
| mindgap nodes/edges | auto |
| global-learnings tier-1 rows | auto (dedup first; a row step 2 wrote this session is a phase-4 candidate, not a dedup hit) |
| mechanical fixes (`dead-map`, `stuck`) | auto — `stuck` reset only at mtime >24h AND `Last session` not today; a `dead-map` id is never synthesised |
| project `CLAUDE.md` | **gated — show diff, wait** |
| `~/.claude/skills/**` | **gated** |
| `<project>/.claude/skills/**` | **gated** |
| any retire / delete, anywhere | **gated — show list, wait** |

Gated means: show the exact diff or list before writing. Never bundle a
gated change behind an auto one, and never read a completed loop as
consent — a loop finishing is why this skill ran, not approval for what
it wants to write.

**A gate never blocks a session.** This skill is invoked from
`loop-system` SESSION END, which may run unattended. Human present → show
the diff and wait. No human present → do NOT halt: record the proposal in
ledger §7 as `status:proposed`, surface it in the phase-7 report, and
return control. A distill that blocks stalls SESSION END step 4
(auto-continue) and burns the loop's remaining wakeups. The gate prevents
an unreviewed write; it does not hold a session open.

### Skill rules — this skill owns creation and destruction

`loop-system`'s structure pass NOMINATES; nothing there writes under a
`skills/` path. This phase decides. It is the only component that reads every
loop in the project and the whole flat cross-project ledger (rows carry no
project field, so the mandated dedup is a whole-file read), and the only one
that can spawn a verifier.

- **Create** — a nomination at `used: ≥1`, phase-4 `HOLDS` on its underlying
  fact, and a human approving the diff. `UNPROVABLE` → withhold and leave the
  row a candidate; never self-verify inline; never promote on judgement alone.
  On approval write `status:promoted→<skill-path>` into the mirrored `gl-*`
  node BEFORE pruning the ledger row (two stores, no transaction).
- **Destroy** — today only the *motivating-learning-falsified* trigger has a
  real observation channel. Retire on that; treat the workaround-shape flag as
  advisory and never as a promotion block.

**Prefer not promoting while retirement is weaker than promotion.** Promotion
prunes the row, so `used:`/`last:` stops at that moment and nothing counts a
rule's firings afterwards — three of the four retirement triggers are inert.
Until a promoted row leaves a stub carrying its counter, this system can add
skill rules far more reliably than it can remove them. That asymmetry is a
known open defect: hold promotion to rules whose evidence you would still
defend if you could never take them back.

**Do not wait on loop completion alone.** This skill fires when a loop
completes or force-escalates — but many loops never write a conformant
completion line, and standing loops (recurring scans) never complete by
construction. Their nominations would be
decided never. Also run the skill-rule pass when invoked manually, or when the
oldest outstanding nomination exceeds three sessions.

`CLAUDE.md` is written only between the `<!-- loop-distill:begin -->` and
`<!-- loop-distill:end -->` markers, regenerated in place and capped at
~25 lines (full contract: `references/promotion-protocol.md`). Never
write outside the markers — the hand-written parts belong to the user, so
contradictions found there are reported as proposals.

A rule earns a place in that block only if it is **`HOLDS` from phase 4
AND changes what ANY session does in this project** — both halves, and
routed here rather than to any other destination. Often nothing clears
that bar, so: **no qualifying rules → no block.** Never write an empty or
header-only block. If a block already exists and none of its rules still
qualify, propose removing it — a gated delete — rather than leaving stale
guidance in the file every session reads. Either way, phase 7 says which
case applied.

## Phase 6 · mindmap

With the mindgap MCP available: mirror, mine, adjudicate — the
protocol is in `references/promotion-protocol.md`. Mirror project → loops
→ learnings and repair dangling `map:` ids, never leaving an island —
fallback anchor `loop-system-global-learnings`. Use the graph's own
vocabulary, never an invented term: `created_by loop:<project>-distill`
(the MCP accepts only `loop:<name>`, `manual`, `mcp`), project node type
`concept`, loop node type `process`, learnings `learning`, edges
`relates_to` / `part_of`. Mine with `mindgap_mine_connect` (latent
links), `mindgap_mine_enrich` per loop goal (2–3 hops), and
`mindgap_mine_learn` (thin spots, stubs). Then adjudicate every
suggestion in the orchestrator: mined links are hypotheses, not findings.
Confirmed ones are ingested; the rest land in ledger §8 as ideation and
candidate next loops.

MCP unavailable → skip the phase and say so in the report. That is not an
error, but an unmentioned skip reads as a clean map.

## Phase 7 · report

One short block, no prose recap of the ledger — the ledger is the
artifact:

- loops seen, with status and any `live` marks;
- flags by type, with counts;
- promotions made, with their verdicts — **and every candidate withheld**,
  with why: `STALE`, or `UNPROVABLE` because no verifier subagent could be
  spawned. A withheld candidate is a ledger §7 row ending `status:withheld`,
  never a silent omission;
- **what happened to the `CLAUDE.md` block** — regenerated, proposed for
  removal because no rule still qualifies, or **not written at all
  because nothing qualified**. State the last case in words; it is the
  one a reader handles by silently doing nothing, and an unreported
  no-block is indistinguishable from a phase that never ran;
- **every proposal awaiting approval** — list each ledger §7 row this run
  wrote `status:proposed`, with its exact next action. Never omit these:
  reporting them is what makes an unattended gate safe, and a proposal
  recorded but unreported is a silent no-op nobody ever approves;
- ideation candidates from §8, one line each.

Then write ledger §9's run-log line.

## Guardrails

- **Never a gate.** No flag, verdict, or ledger row can fail a loop,
  block a session, or count against a loop's criteria. This is advisory
  memory hygiene; a loop's only gate is its GOAL §2 criteria. This skill's
  own write gates block a write, never a session — unattended, a gated
  change is recorded `status:proposed` and reported, never waited on.
- **Never race a live loop** — and LIVE takes **both halves**: STATE shows
  `session-in-progress: yes` **AND** STATE mtime is under 6h. Read-only on
  such a loop, including its `## Consult` seeding. An in-progress flag over
  an mtime older than 6h is `stuck`, not live — phase 2 flags it, and
  resets it only under the wider >24h + `Last session`-not-today
  conditions. Dropping the mtime half here would forbid the very `stuck`
  reset and `## Consult` seeding that phases 2 and 5 mandate.
- **No unattended outward action.** No gated surface is ever written
  without a human, even when `loop-system` invoked this skill
  automatically at SESSION END — the write is deferred as a proposal, not
  taken.
- **One destination per learning**, deduped before every write.
- **Report what was skipped** — an absent MCP, a live loop, a gate still
  waiting. Silence reads as clean.
